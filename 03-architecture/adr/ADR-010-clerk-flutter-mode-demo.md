# ADR-010 — Mobile auth via Clerk Flutter SDK (beta), and a demo mode
**Status:** accepted · 2026-09-18
**Context:** F5 requires Clerk (ADR-002) with Google and email. Clerk has no stable Flutter SDK: `clerk_flutter` is announced in beta (Clerk changelog 26/03/2025), published by clerk.com but "community-maintained", with the instruction to pin the patch version. The alternative is talking to Clerk's Frontend API manually: the email + code flow is simple, but Google OAuth requires a browser, a deep-link return and session management — several days for a solo developer 12 days from the deadline.
**Decision:** `clerk_flutter` + `clerk_auth` pinned to exact version (`0.0.18-beta`), prebuilt sign-in screen (`ClerkAuthentication`, displayed strategies are those in the dashboard), token via `ClerkAuthState.sessionToken()`. The rest of the app only sees the `AuthSession` contract (`core/auth/auth_session.dart`): `isSignedIn`, `user`, `token()`, `signOut()`, observable.
Corollary: **a demo mode**. Without `--dart-define=CLERK_PUBLISHABLE_KEY`, the app runs on a dummy session and an in-memory repository (`MockLymarksRepository`, same business rules as the API). This is the mode for tests, golden renders, and any machine without a key. CI refuses to produce an APK without a key.
**Alternatives:** home-grown Frontend API (cost, risk on OAuth); Firebase Auth (breaks ADR-002); defer auth (impossible: F6 and F7 depend on it).
**Consequences:**
- By default the SDK opens Google OAuth in a WebView with a spoofed user-agent; **observed failing on device on 18/09** (the user had to sign up via email). Replaced the same day by the SDK's browser flow: `redirectionGenerator` → `lymarks://oauth/<strategy>`, opened in a Custom Tab (`LaunchMode.inAppBrowserView`), return via deep link (`app_links`, intent-filter `lymarks://oauth`), URL allowlisted on the Clerk instance (`POST /v1/redirect_urls`, to redo on the production instance).
- **The deep link return is handled by the app, not the SDK** (`ClerkAuthSession.handleDeepLink`, validated on device 18/09 at 17:29). Two SDK 0.0.18 bugs require it: (1) without a nonce — the case of an unknown Google account, where Clerk creates no session and marks the attempt `transferable` — `refreshClient()` rejects any response whose `client.updated_at` is not strictly newer, yet Clerk does not advance it when an attempt progresses (the SDK's own comment): the attempt stays `unverified`, the transfer never happens; (2) `completeOAuthSignIn` does nothing, silently, if the attempt has disappeared. The app therefore goes through `fetchApiResponse` (the SDK's public low-level API, which sets headers, updates the rotating client token and applies the `Client`): `GET /client` without nonce or `GET /client/sign_ins/{id}?rotating_token_nonce=` with it, then `POST /client/sign_ups` (or `sign_ins`) with `transfer=true` if verification is `transferable`. To revisit when SDK 1.0 ships.
- 60 extra transitive dependencies (webview, url_launcher, passkeys, image_picker…): to measure on the APK (40 MB budget).
- No SDK upgrade during the sprint (Coding Standards §5); review after the Shipaton, migrate to 1.0 when it ships.
- State logic (`LymarksNotifier`, search, profile) is tested on the in-memory repository and the HTTP client on a `MockClient`: 37 tests, no network, no SDK.
